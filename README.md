# monitor — внешний мониторинг Trufill

Независимая проверка продакшна **извне собственной инфраструктуры**: прогон GitHub Actions
каждые 15 минут смотрит на Trufill так же, как его видит внешний мир, и на контракты в Base
mainnet — так же, как их видит любой держатель узла. Сбой превращается в issue в этом
репозитории с назначением на владельца (почта + приложение GitHub), восстановление закрывает
её само.

Репозиторий публичный, потому что минуты Actions публичных репозиториев бесплатны и не делят
квоту организации с приватными. Секретов здесь нет и не должно быть: только публичные URL,
адреса контрактов и эталонное состояние управления.

## Что проверяется

**Доступность (с повторами внутри прогона, чтобы моргание не будило):**

| Проверка | Что именно |
|---|---|
| `api.status` | `/status` шлюза: HTTP 200, общий статус не `down`, журнал котировок `ok`, строка Base: `rpc=ok` и `routerWiring=ok` (иначе котировки Base не выдаются). Тестнеты — только в сведения. |
| `api.health` | `/health`: HTTP 200. 503 = `down`. |
| `swap.app` | Терминал: `index.html` отдаётся, его бандл совпадает с `version.json` и скачивается. |
| `site.pages` | Главная и `accuracy.html`: 200, HTML, в заголовке Trufill. |
| `accuracy.snapshot` | Снимок точности: свежий (< 50 мин, таймер пишет каждые 15), хеш по опубликованному рецепту `snapshotSha256Recipe` совпадает, нарушений порога нет. |
| `tls` | Сертификаты трёх хостов: до конца больше 14 дней. |

**Управление на цепи (Base mainnet, читается через публичные узлы):**

Код четырёх контрактов (sha256), связка роутера (`feeSwitch`, `swapRouter`), FeeSwitch
(комиссия 0 bps, получатель = Safe, владелец = таймлок), таймлок (владелец = Safe, привязка),
Safe (владельцы, порог, nonce, модули, guard, fallback-обработчик, singleton).

Эталон — `config.json` → `base.expected`. Любое расхождение — тревога с расшифровкой
событий управления за последние ~4 часа. Постановка в очередь таймлока невозможна без
транзакции Safe, а та сдвигает `nonce`, поэтому состояние ловит всё, что ловили бы события.

## Как устроена защита от ложных срабатываний

- **Повтор внутри прогона:** каждая HTTP-проверка повторяется до 3 раз с паузами 15 и 30 с.
  Тревога только на сбое, пережившем ~45 секунд.
- **Два независимых узла:** расхождение состояния цепи подтверждается чтением со второго
  узла Base; не подтвердившееся — сбой узла, а не изменение управления (уходит в сведения).
- **Отставшие узлы отбрасываются:** узел с головой старше 180 с не годится для чтения —
  он ответил бы «как было».
- **Открытие сразу, закрытие не сразу:** issue открывается с первого уверенного сбоя, но
  закрывается только после двух чистых прогонов подряд — моргающий сбой не хлопает
  тревогой каждые 15 минут.
- **Код прогона всегда зелёный:** сбои проверок идут в issue, а не в exit code. Красный
  прогон workflow означает сломанный монитор, и об этом GitHub пишет владельцу расписания
  отдельным письмом.

## Тревога

Одна открытая issue с меткой `monitor-alert`. Её состояние (что сбоит, сколько чистых
прогонов подряд) хранится в скрытом комментарии тела самой issue — расписание Actions не
имеет памяти между прогонами. Пока состав сбоев тот же, тело правится молча (правка не шлёт
уведомлений); изменился — комментарий, он уведомляет. Каждая строка сбоя снабжена
подсказкой «что делать» (куда смотреть на сервере, что откатить, что обновить в конфиге).

## Эксплуатация

**Проверить прямо сейчас, с локальной машины** (сеть живая, GitHub не трогается):

```bash
node src/main.mjs --dry-run            # с повторами, ~1 мин при сбоях
node src/main.mjs --dry-run --no-retry # диагностика: сбой виден сразу
```

**Учебная тревога:** Actions → monitor → Run workflow → `drill: true`. Откроется issue
«Учебная тревога мониторинга»; два следующих чистых прогона (можно запустить вручную тем же
кнопкой без drill) закроют её сами.

**Изменилось управление — это было ожидаемо** (например, добавлен второй ключ Safe):
правим `base.expected` в `config.json`, тревога закроется сама после двух чистых прогонов.
Хеши кода пересчитать: `cast code <адрес> --rpc-url <rpc> | xxd -r -p | sha256sum`.

**Тесты:** `npm test` (Node ≥ 20, зависимостей нет).

## Границы

- Публичные RPC Base — это точка отказа наблюдателя: если все три недоступны с раннера
  GitHub, проверки цепи краснеют как `base.rpc` («слепы»), а не выдумывают состояние.
- Расписание Actions имеет джиттер и не гарантирует период; для субминутной доступности
  нужен другой контур.
- Монитор не мерит латентность и не проверяет котировки по смыслу — только живость,
  целостность и управление.
